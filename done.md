### T5. Unicode tables

`scull-unicode`: multi-stage width and grapheme-break tables generated from the Unicode data files, one width function shared by the scanner and the grid, mode 2027, and a setting for ambiguous width and Unicode version. Done when `GraphemeBreakTest.txt` passes and emoji ZWJ, variation selectors and combining marks have golden tests.


Execution plan:
1. Evaluate `unicode-width` and `unicode-segmentation` against a per-code-point table (configurable ambiguous width, incremental grapheme state); record the choice in the commit.
2. A generator (workspace binary under `tools/`) reads pinned Unicode data files checked by SHA-256 and writes multi-stage tables into `crates/scull-unicode/src/tables.rs`, committed; a test fails when the output is stale.
3. `crates/scull-unicode`: `width(cp, opts)`, incremental grapheme-break state, cluster width for mode 2027, ambiguous-width and Unicode-version options.
4. Tests: `GraphemeBreakTest.txt` in full; golden tests for emoji ZWJ, variation selectors and combining marks.
5. Verify with `just check`. Over the 500-line budget, split the rest into T5.x.

Delivered: own three-stage tables (about 15.7 KB) generated by `tools/scull-ucd-gen` from Unicode 18.0.0 data files pinned by SHA-256 (`just ucd`, `just ucd-check`). `unicode-width` and `unicode-segmentation` were rejected: no per-code-point incremental grapheme state and no selectable Unicode version. API: `width`, `GraphemeState`, `ClusterWidth` with `ClusterPolicy` for mode 2027, `AmbiguousWidth`, `UnicodeVersion`. All 853 `GraphemeBreakTest.txt` lines pass; golden tests cover emoji ZWJ, flags, skin tones, VS15/VS16, combining marks, Indic conjuncts, Hangul, CJK and ambiguous width. VS15 keeps the width, as the mode 2027 spec says; kitty, foot and Contour narrow it to 1, which desynchronises `wcwidth`-based applications (creator chose the spec). Left open: only Unicode 18 tables exist; no ASCII fast path; the stale-table test is skipped in CI without the data cache.

### T4. Parser

`scull-parser`: a bulk scanner that delivers text up to the next control byte as one run, in front of a table state machine for CSI, OSC, DCS and APC, emitting typed actions. Payloads are dispatched in place with hard length caps. Done when the fuzz target runs clean and throughput on plain text beats `vte` in the T3 benchmark.


Execution plan:
1. Pick the state machine: `vtparse` behind our scanner (research.md §6) or our own table after Paul Williams' DEC parser; record why in the commit.
2. `crates/scull-parser`: bulk scanner (printable UTF-8 runs up to the next control byte as one `&str`, split UTF-8 kept across `feed` calls), CSI with colon sub-parameters, ESC, OSC, DCS and APC delivered in place to a handler trait; hard caps on parameters, intermediates and payload lengths, each with a test.
3. `fuzz/` workspace (cargo-fuzz, nightly) with a parser target; run it clean locally.
4. A divan bench in `crates/scull-parser/benches` against `vte` on plain text and mixed SGR output.
5. Verify with `just check`. Over the 500-line budget, stop at a coherent boundary and split the rest into T4.x.

Delivered: own Williams-table state machine behind a SWAR bulk scanner (`vtparse` buffers APC in an unbounded Vec and parses byte by byte; `vte` drops APC). `Parser::feed` hands printable UTF-8 runs to `Handler::print` in one piece, keeps a split UTF-8 character across calls, streams DCS and APC payloads as input slices, and keeps OSC in one reused buffer. Caps: 32 params, 2 intermediates, OSC 1 MiB, DCS 16 MiB, APC 4 MiB, each with an overflow test. 46 tests including a chunking-invariance property. Fuzz target `parser`: 5,081,125 runs in 121 s, no crashes after an underflow fix. divan bench against vte 0.15 on 1 MiB: plain ASCII 3.05 vs 1.22 GB/s (2.5x), UTF-8 1.31 vs 0.80 GB/s (1.6x), SGR-heavy at parity. Left open: the bench is parser-level, not yet wired into the T3 harness; no flush for a UTF-8 character held when the PTY closes; a UTF-8 C1 ST (U+009C) does not end a string; about 685 lines of non-test code, over the 500-line budget.

### T6. Grid and scrollback

`scull-grid`: a small fixed cell with interned clusters and styles, rare data out of line, O(1) blank and uniform lines, and one power-of-two ring of lazily allocated rows shared by the screen and scrollback. Rows carry a stable id and a generation. Done when scrolling is an offset change and memory per scrollback row is recorded in the benchmark.


Execution plan:
1. Read the ring storage of Alacritty (`alacritty_terminal` grid/storage) and the cell layouts recorded in `docs/research/`; port from upstream Alacritty or WezTerm only with notices kept.
2. `crates/scull-grid`: a fixed-size `Cell` (cluster id, style id, flags incl. wide/spacer), interning tables for clusters and styles with hard caps, rare data (hyperlink ids, underline colour) out of line, rows with a stable id and a generation, O(1) blank and uniform rows.
3. One power-of-two ring of lazily allocated rows shared by the screen and scrollback with a hard scrollback cap; scrolling is an offset change.
4. Tests for every cap and for scroll as offset change; a divan bench that records memory per scrollback row.
5. Verify with `just check`. Split at claim: T6.1 cells, interning and rows; T6.2 ring and scrollback; the agent reports which landed.

Delivered (T6.1 and T6.2): an 8-byte `Cell` (inline code point or cluster id, `StyleId(u16)`, flags) checked by a const assert; wide characters as head plus spacer cells with repair on partial overwrite; styles (colours, underline colour and shape, attrs) and clusters interned with caps of 65,536 each and 32 code points per cluster, reclaimed by mark-and-sweep that runs only when it pays for itself, with `intern_epoch()` telling T7 to re-intern held ids; rows with a stable `RowId`, a `generation` bumped on visible change, a stored prefix plus a fill cell for O(1) blank and uniform rows, and out-of-line link spans; one power-of-two ring shared by screen and scrollback (`MAX_RING_ROWS` 131,072), scrolling as an offset change, region scrolls, viewport pinning and ED 3. 44 tests including a ring-invariant proptest. Bench at 120 columns: 56 B per blank, 632 B per plain-text and 1016 B per SGR-heavy history row; a full-ring scroll takes 25-66 ns with no allocation. Nothing ported; ideas from foot, Alacritty, Contour and kitty. Left open: reflow (T11), damage collection (T9), the meaning of `LinkId` (T13), replacing the `scull-harness` stub with the real grid; about 656 lines of non-test code in T6.1, over the 500-line budget.

Left open: wiring `CSI = > < ? u` into the stack (scull-term), DECBKM, formatOtherKeys, modes 1001, 1007 and 5522, no comparison run against a real xterm; T12.1 is about 970 lines of non-test code, about 300 of them key tables, over the 500-line budget.

### T8. PTY and I/O thread

`scull-pty`: a reader thread per terminal on top of a PTY crate, bounded work per lock hold, `try_lock` with back-pressure, replies written from the same thread, child exit through the same loop. ConPTY on Windows. Done when a flooding child cannot starve a frame read and a shell runs on both platforms.


Execution plan:
1. Re-check `portable-pty` maintenance (research.md §6) against alternatives on crates.io; pick one and record why.
2. `crates/scull-pty`: spawn a child on a PTY (ConPTY on Windows), a reader thread per terminal that hands bounded chunks to a caller-supplied sink, `try_lock`-style back-pressure through a trait so the crate stays independent of scull-term, replies written from the same thread through a capped queue, resize, and child exit delivered through the same loop.
3. Tests: a flooding child (`yes`) cannot starve a concurrent reader of the shared state; a shell runs `echo` and exits with its status; resize reaches the child; on Windows the same tests through ConPTY.
4. Verify with `just check`.

Delivered: `Pty::spawn` over `portable-pty` 0.9.0 (the only maintained cross-platform crate with ConPTY) with a caller-supplied `Sink` behind a `parking_lot::Mutex`; separate reader, I/O-loop, writer and wait threads because the PTY handles block uninterruptibly. The loop feeds at most 64 KiB per lock hold and releases with `unlock_fair`; the reader blocks once 1 MiB is pending (back-pressure); replies and input share a 256 KiB write queue; child exit arrives last through the same loop, with an idle and drain timeout for ConPTY and orphaned children. Starvation test: with `yes` flooding, 809 frame reads in 2 s waited at most 163 us (13 ms with a plain unlock), 250 MB fed. 25 tests. Windows: `cargo check` and clippy pass for `x86_64-pc-windows-msvc`. Left open: no run on a Windows host, no SIGKILL escalation, no test for the post-exit drain cap.
