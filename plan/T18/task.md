# T18. Windows input method and accessibility

TSF text input and a UIA text provider, written in C#. Windows Terminal's C++ implementation is the reference to read, not code to link. Done when CJK input and Narrator reading work.

Execution plan (split to fit the budget, mirroring T16):
- T18.1. Pure UIA text model in `windows/Scull.Core`, no WinUI or interop types, mirroring `macos/Sources/ScullKit/ScreenText.swift`. New `ScreenText.cs`: the viewport text from `Terminal.ReadText` (one line per row, UTF-16 offsets), `LineFor(offset)`, `RangeForLine(line)` (the line with its newline), `OffsetOf(line, col, width)` and `Columns` (a wide character takes its cells), the cursor's offset, `GetText(range)`, `LineSpans(range)` for bounding rectangles. New `TextRange.cs` and `TextUnits.cs`: `TextRange` (start, end), `TextUnit` and `TextEndpoint` with the `UIA_TextUnit` and `TextPatternRangeEndpoint` values, and the `ITextRangeProvider` operations as pure functions over the text: `ExpandToEnclosingUnit`, `Move`, `MoveEndpointByUnit` (character = grapheme cluster, word = a run of letters and digits or of punctuation plus the spaces after it, each CJK ideograph or kana alone, a newline alone; line and paragraph = row; format, page and document = the whole text), each returning the units actually moved. New `TextChange.cs`: the first and last changed line between two texts, none when equal, so the host raises `TextChanged` only for a real change. Verify: MSTest in `Scull.Core.Tests` on every runner (offsets and lines, clamping, wide and combining characters, every unit's expand and move in both directions, endpoint moves that cross, change detection, and a real `Terminal` fed CJK text whose cursor offset and spans match its frame cells); `just check`, `just windows-core-test`, `dotnet build` with warnings as errors. Narrator and a real IME need a human.
- T18.2. WinUI `AutomationPeer` and text provider over the T18.1 model. The panes are not XAML elements (they are regions of the window's one swap chain), so the peer belongs to the keyboard-focus control, which becomes a `TerminalHost : UserControl`, and it exposes the focused pane of the selected tab, the one that takes the typing. Pure pieces first, in `Scull.Core` where every runner tests them: `TextSnapshot` (a `ScreenText` with the frame's cell widths, the cursor's offset and the pane's `CellGeometry`, captured once per UIA call so a range stays valid while output goes on; its `Rectangles(range)` for bounding rectangles in swap-chain pixels from the cell size and the pane's area, `RangeAt(x, y)` for hit tests, `Caret`), `ScreenText.Find` for `FindText`, `TextRange` endpoint helpers (`CompareEndpoints`, `WithEndpoint`, shared with `MoveEndpointByUnit`), and `TextChangeTracker` (reads and compares the text only while a client listens). In `Scull.App`, new files: `TerminalHost.cs` (`OnCreateAutomationPeer`), `TerminalAutomationPeer.cs` (`FrameworkElementAutomationPeer` with `ITextProvider`, control type Document, `TextPatternOnTextChanged` raised after a redraw when `AutomationPeer.ListenerExists` says a client listens, screen rectangles from the peer's bounding rectangle plus the pane pixels) and `TerminalTextRange.cs` (`ITextRangeProvider` as a thin adapter that casts the UIA unit and endpoint values, which match ours, and calls the model). The hook into existing files is small: `TerminalPane.Snapshot()`, `TerminalWindow` making the host and calling `host.TextChanged()` at the end of `Redraw`. Not done here: one child peer per pane, selection (the pattern says none is supported), attribute queries. Verify: MSTest for each pure piece on every runner (a real `Terminal` with CJK text); `just windows-app` on the Windows runner builds the adapter; `just check`, `just windows-core-test`, warnings as errors. Narrator reading, Accessibility Insights and the real `ITextRangeProvider` marshalling need a human on Windows.
- T18.3. TSF text input in `Scull.App`: a text store with the preedit carried through `tt_frame_preedit` and committed text through `Terminal.Text`, the composition window placed at the cursor. Pick: a TSF context owner with no text store of our own (`ITfThreadMgrEx.ActivateEx` with `TF_TMAE_CONSOLE`, `ITfDocumentMgr.CreateContext` with no store, `ITfContextOwner`, `ITfContextOwnerCompositionSink` and `ITfTextEditSink` implemented by us, the composition read back through an edit session). This is what Windows Terminal ships (`src/tsf/Implementation.cpp` in microsoft/terminal at 44b440b, checked 2026-10-16) rather than `ITextStoreACP2` or the WinRT `CoreTextEditContext`: the terminal has no editable document to answer `GetText`/`SetText` for, the context-owner route reports `TS_SS_TRANSITORY` so that finished text is not expected to stay in the document, and that file states the WinRT `CoreTextServices` APIs do not set `TS_SS_TRANSITORY`. The COM interfaces come from Microsoft.Windows.CsWin32 0.3.358 (already the repo's pick, `research.md` §6.1), added to `Scull.App` with its own `NativeMethods.txt`, and our three sinks and the edit session are one hand-built vtable block like `Scull.Render/TextAnalysis.cs`. Pure pieces first, in `Scull.Core` where every runner tests them: `Terminal.SetPreedit(text, caret)` over `tt_frame_preedit` (UTF-16 caret to UTF-8 byte offset) and `FrameView.Preedit` (the span the core marks); `CompositionTracker` (composition count from `OnStartComposition`/`OnEndComposition`, active, an update pending after the last one ended); `CompositionText.Split` (the ranges TSF returns with their composing flag into the finished text to send and the active text to show, as Windows Terminal does, and the caret clamped into the active text); `CellGeometry.Box(row, col, cells)` for the candidate window's rectangle from the cell size and the pane's area; `WindowsKeys.IsProcessKey` (VK_PROCESSKEY). In `Scull.App`: new `TsfInput.cs` (the COM side: activate, document and context, sinks, focus, `GetTextExt`/`GetScreenExt`/`GetWnd`/`GetStatus`, the edit session that reads the composition) and `TerminalInputMethod.cs` (glue to the window: focus in and out, the preedit into the focused pane, committed text through `Terminal.Text`, the candidate rectangle in screen pixels from the pane's `Area`, `Metrics` and the host's position, no pane code). The hooks into existing files stay small: `TerminalWindow` makes the input method and calls `Intercept` first in `OnKeyDown`/`KeyUp` and skips `CharacterReceived` while a composition is active, so the keys an IME takes (VK_PROCESSKEY, and the characters of a composition) never reach `WindowsKeyPairing`; a pending composition is flushed before any other key, so Enter commits before it is sent. `TerminalPane` gets only a `SetPreedit` pass-through. Not done here: per-clause display attributes (the core marks one span), reconversion, the IME's on/off state. Verify: MSTest for each pure piece on every runner (a real `Terminal` fed a preedit with CJK text, the span and caret in the frame; the tracker; the split; the box; the key test); `just windows-app` on the Windows runner builds the COM side; `just check`, `just windows-core-test`, warnings as errors. A real Japanese or Chinese IME (composition, candidate window position, Enter committing, Escape cancelling) needs a human on Windows.
- T18.4. The UIA text provider exposes the terminal's selection (T17.8 gave the core one). `SupportedTextSelection` becomes `Single`; `GetSelection` returns the selected range, or the empty range at the cursor when nothing is selected, as Windows Terminal does; `TextSelectionChanged` is raised when a gesture, output or a client changes it; `ITextRangeProvider.Select` selects the range's cells through the core. `AddToSelection` and `RemoveFromSelection` stay unsupported: the core has one selection. The pure mapping is in `Scull.Core`: `Cell.IsSelected` (`TT_CELL_SELECTED`), `TextSnapshot.Selection` (the first to the last selected cell of the viewport frame as a `TextRange`, widths and wide characters honoured), `TextSnapshot.CellsOf(range)` (the cells a range covers, for `Select`), and `SelectionTracker` (reports a change only while a client listens, as `TextChangeTracker` does). Limits, written here: a block selection is one range from its first to its last cell, so the cells between that it did not select are inside the range; only the part of a selection in the viewport is marked by the frame, so one scrolled out of view reads as no selection. Execution plan: (1) `Cell.IsSelected` and `TextSnapshot.Selection`/`CellsOf`, MSTest against a real `Terminal` (select, read the range back and compare its text with `SelectionText()`, wide and CJK cells, a multi-row selection, a selection of blanks, none). (2) `SelectionTracker` and its tests. (3) `Scull.App`: the peer's `SupportedTextSelection`, `GetSelection`, `RaiseTextChanged` also reporting selection changes, `TerminalTextRange.Select` calling a window callback that runs `Terminal.Select`/`ExtendSelection` on the focused pane. Verify: `just check`, `just windows-core-test`, CI incl. `just windows-app`; Narrator reading a selection needs a human on Windows.
- T18.6. UIA text attribute queries on Windows (T18.2 left them out: `GetAttributeValue` and `FindAttribute` reported nothing). The pure mapping is in `Scull.Core`: `TextSnapshot` also keeps each cell's style (`StyleAt`) and, when the host gives a `TextLook` (a style-to-colours function from the palette, the pane's font family and size in points), exposes `TextSnapshot.Attributes`. `TextAttributes.Get(range, id)` answers font name and size, foreground and background (resolved through the palette, as COLORREF), font weight (bold 700, else 400), italic, hidden, read-only (always false), and the underline, strikethrough and overline line styles; a range whose characters differ answers mixed, an attribute the terminal does not report answers unsupported; an empty range reads the character it sits on. `TextAttributes.Find(range, id, value, backward)` returns the first (or last) run of characters with that value, cut to the range. `Scull.App`: `TerminalPane.Snapshot` passes the look, and `TerminalTextRange.GetAttributeValue` returns the value, `DependencyProperty.UnsetValue` for mixed and an `E_NOT_SUPPORTED` failure for unsupported (the dxaml layer maps these to UI Automation's reserved values: microsoft/microsoft-ui-xaml `UIAPatternProviderWrapper.cpp` and `TextRangeAdapter_partial.cpp`, main, checked 2026-10-17); `FindAttribute` calls `Find`. Verify: MSTest on every runner with a real `Terminal` fed SGR text (each attribute, mixed ranges across styles, rows and wide cells, empty ranges, find both ways with numbers of any boxed type), `just check`, `just windows-core-test`, CI incl. `just windows-app`. Not done: underline and strikethrough colours, per-pane peers (T18.5).
- T18.7. Per-clause preedit display (T18.3 left it: the core marked one span). Core and C ABI: `scull-term` `PreeditClause` (byte range and `ClauseKind` input/converted/target), `Frame::set_preedit_clauses` and `Frame::preedit_spans` (the shown clusters grouped into column runs, a changed clause is row damage through the preedit hash); `tt_frame_preedit_clauses` and trailing `tt_frame_view.preedit_spans`, ABI minor 10 (`tt_frame_preedit` stays and means no clauses). Untidy clauses from the input method are cut to the text, onto character boundaries, without overlap. Windows: `Scull.Core` `CompositionClauses` maps UTF-16 clauses to UTF-8 byte ranges (`Terminal.SetPreedit` takes them), `FrameView.PreeditSpans`, `TsfInput.cs` reads `GUID_PROP_ATTRIBUTE` over the composition (`ITfCategoryMgr.GetGUID`, `ITfDisplayAttributeMgr.GetDisplayAttributeInfo`, `TF_DISPLAYATTRIBUTE.bAttr` to a kind), and the renderer draws input thin dotted, converted thin solid, target thick. Verify: Rust tests (`scull-term`, `scull-ffi`), `just bindings-check`, MSTest on a real `Terminal` for the mapping and the spans, `just check`, `just windows-core-test`.
