# T33. Jump between shell prompts with OSC 133 marks

Shells that emit OSC 133 mark where each prompt starts; the core reports the marks as events but keeps no positions. Done when the core remembers prompt lines in the scrollback (dropped as history is trimmed), exports a call that scrolls the viewport to the previous or next prompt, and both shells bind it to a key (Ctrl+Shift+Up/Down on Windows, Cmd+Up/Down on macOS), with Rust tests for the marks and the jump and a test per platform for the binding.

- T33.1 Core: the prompt lines and the jump. Execution plan: (1) `ScreenImages` (`images.rs`, the per-screen absolute line numbering that already survives scrolling, trimming and ED 3) keeps `prompts: Vec<u64>`, the sorted absolute lines of `OSC 133;A` marks; they are recorded on the primary screen only (the alternate screen has no history to jump in), deduplicated, and dropped when their line leaves the ring (`prune`), when ED 3 clears history, and when ED 2 wipes the screen rows they sit on (like image placements). RIS keeps the scrollback in this core, so it keeps the marks too. (2) A resize rewraps the primary screen, so the marks ride along as `TrackPoint`s next to the image anchors (`anchors`/`reanchor`) and a mark whose row is lost is dropped. (3) `Terminal::scroll_to_prompt(forward) -> bool` moves the display offset so the previous (or next) prompt above (below) the viewport top is the top row, or the live screen when the prompt is on it; false, and nothing moved, when there is none. (4) `tt_term_scroll_to_prompt(term, forward)` in `input.rs` beside `tt_term_scroll_display` (its own block in the header and `lib.rs`; `TT_OK`, or `TT_EMPTY` when there is no such prompt), ABI minor 8 to 9 (after T31's 8), header and C# bindings regenerated with `just bindings`. (5) Rust tests: marks recorded, previous/next walk, no prompt answers `TT_EMPTY`, history trimming and ED 3 drop marks, ED 2, alternate screen ignored, a rewrapping resize keeps the marks on their lines, FFI export. Verify: `just check`, `just macos-test`, `just windows-core-test`, CI Windows jobs.
    Landed: T33.1. Prompts are kept in `ScreenImages` (the existing absolute numbering) and tracked through reflow with the image anchors; `Terminal::scroll_to_prompt` and `tt_term_scroll_to_prompt(term, forward)` (ABI minor 9, after T31's 8; own module `prompt.rs`, own line in the csbindgen source list) answer `TT_EMPTY` when nothing moves. Differences from the plan: a full reset (RIS) keeps the scrollback in this core, so it keeps the marks above the screen and drops only those on the blanked rows; a jump to a prompt that is on the live screen scrolls to the bottom. Not verified by hand: a real shell with OSC 133 integration; the Windows jobs and the C# build see the new export only through CI.
- T33.2 Both shells bind the jump. Execution plan: Cmd+Up/Down on macOS and Ctrl+Shift+Up/Down on Windows through the existing command tables (`PaneCommands.cs` and the macOS key-binding table), calling `tt_term_scroll_to_prompt` and redrawing; a test per platform for the binding; Windows `Terminal.cs` gets the binding of the new export.
    Landed: T33.2. macOS goes through the config action table, so the jump is rebindable like the scroll actions: `Action::PreviousPrompt` and `NextPrompt` (`TT_ACTION_PREVIOUS_PROMPT` 9 and `TT_ACTION_NEXT_PROMPT` 10, defaults `super+up` and `super+down`, schema regenerated) and `TerminalView.runBinding` calls `tt_term_scroll_to_prompt` through `TerminalSession.scrollToPrompt`. Windows has the fixed `PaneCommands` chord Ctrl+Shift+Up/Down (`PreviousPrompt`, `NextPrompt`; Ctrl+Up alone stays the program's), `Terminal.ScrollToPrompt`, and also runs the two config actions, so a `[[keybind]]` works there too. Tests: Swift `PromptJumpTests` (viewport walk, Cmd+Up/Down through `performKeyEquivalent`, the default keybinds), Rust defaults in `scull-config`, C# `PromptTests` (the wrapper over the real library) and the `PaneCommands` data rows. Not verified by hand: a real shell with OSC 133 integration; the C# tests, which did not run on this machine (the .NET workload install is broken) and are covered by the Windows CI jobs only. No second ABI bump: the new constants went into the minor 9 of T33.1.
